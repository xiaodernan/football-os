# DATA_POLICY — FOOTBALL OS

## 1. Provenance classes

Every persisted row carries `data_origin`:

- `synthetic` — generated by our own world builder (fictional names, no real-world claim). Displayed as **DEMO DATA**.
- `project-authored` — written by this repository as content, not as a simulation of the world: the knowledge corpus (`data/knowledge`) and the 50 tactical systems (`app/services/tactics`). Displayed as **PROJECT AUTHORED**, never as `DEMO DATA`, because labelling an authored document "demo" understates it and labelling generated football data "authored" overstates it.
- `licensed` — obtained through a contracted provider behind `FootballDataProvider`/`NewsProvider`, with provider id, licence ref, retrieved-at. **No such row exists yet**: no provider key is configured, so `provider_status()` reports `source: local synthetic world`.
- `open` — legally open/public data with source URL and citation. Also not yet implemented.
- `user` — uploaded/created by a user; the user is the data controller of that content, we are the processor.

Mixed provenance in one visual surface is forbidden; each card labels its class.

## 2. Never do

Scrape paid/protected databases (Opta, StatsBomb, Sportradar, FC/FM data). Copy player photos, club crests, broadcast video, or any EA/FIFA/FM asset. Imply official affiliation. Invent statistics when a metric is unavailable — render `Data unavailable` instead.

## 3. Personal data

Categories collected: account (email, display name), football identity (position, age band, attributes, goals), training logs, optional self-reported physical data, optional user-uploaded video.

Purposes: deliver the requested training/coach function, store the user's progression history, and — only with explicit consent — community/SEO publication.

Rights, stated as what the code actually serves today rather than as a promise list:

- **Export** — `GET /api/v1/progress/export` returns every row the account owns as JSON (the settings page links it).
- **Delete my football data** — `DELETE /api/v1/progress/player-data` removes the player and its dependent
  rows (attribute history, sessions, XP events). The UI names what that destroys and confirms first.
- **Consent ledger** — registration requires `accepts_data_policy`, and `/settings` shows the stored
  acceptance plus the policy text it accepted.
- **Account erasure — implemented, and walked.** `DELETE /api/v1/auth/account` erases the account: the
  rows it owns are deleted through the schema's own cascade, the rows that have no foreign key to it
  (jobs, knowledge queries, revoked tokens, usage events) are deleted explicitly, the *aggregates* —
  provider cost totals and operational action counts — are **retained with the account id removed**
  rather than deleted, so the platform's own accounting survives while the person does not, and the
  account's private media is unlinked from storage with the byte count reported. A phrase
  (`DELETE`) and the current password are both required, the tenant-orphan case is refused **before any
  write**, and `GET /api/v1/auth/account` prints the whole inventory without changing a row, so the
  settings page can name what the button will take before the button is armed. The browser walk proves
  the three refusals and the erasure itself in `apps/web/scripts/visual-qa.mjs` §10a.
  *This paragraph replaced a claim that it was **not** implemented — the door, the service, the preview
  and the panel have been there since the account tier landed, and the policy still said otherwise.*
- **Per-video deletion — implemented, and walked.** `DELETE /api/v1/video/{ident}` removes the clip's row
  **and its stored bytes**: the original and the sampled frames are unlinked from private storage, and the
  clip's analysis jobs go with it. "An upload right implies a take-back-right" is the tier's own sentence
  on the door, and the walk presses the button in a browser: the list empties, the old report address
  answers as unusable, and the file route is gone with the row.
  *This paragraph replaced a claim that it was **not** implemented — the door has been there since M5, and
  the policy still said otherwise.*
- **Not implemented, so not claimed as a feature:** per-entity visibility toggles — a reader cannot yet say
  "this row of mine is not public". It is tracked in [`ROADMAP.md`](ROADMAP.md), and a UI that offered it
  would be a lie, so it does not.

## 4. Minors

Default-deny: private profiles, no precise location, no contact info, no public video, no AI scouting report visible outside the owning academy, parental-consent flag gates any publication. Data minimisation on signup (age band, not DOB, unless a licensed academy needs it).

## 5. Retention & multi-tenancy

UGC retained until deletion request; provider payloads retained per licence terms with `retrieved_at` and expiry; organisations (B2B) get tenant-scoped rows via `organization_id`, and offboarding produces export then purge within 30 days.

## 6. AI outputs

Model-derived assessments are labelled `AI-generated`/`Estimated` with confidence and source list, are not scouting certification, and not medical diagnosis (see `AI_POLICY.md`).
